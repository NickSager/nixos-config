## OM project context

Use OM when recorded rationale could change the work.

- Before changing a project-wide format, identifier semantics, or shared
  interface, use `search`. Use `expand` for a known note's links, `recall` for
  durable lessons, and `health` only when an expected record cannot be found.
- Before implementation, state any recorded decision the change relies on,
  contrary evidence, or "nothing recorded." An empty result is a finding.
- If OM and the repository disagree, reconcile the recorded rationale with the
  repository's current behavior before changing it.
- Before finishing work that changed files or made a durable project decision,
  use `record_work`. Also record findings that future work could not recover
  from the repository.
- Use `remember` for lessons that apply beyond this repository. State their
  confidence and verification honestly.

Skip OM for conversation, status or listing questions, routine read-only
inspection, and facts already clear from the repository. If OM is unavailable
when a record is required, report that failure.
